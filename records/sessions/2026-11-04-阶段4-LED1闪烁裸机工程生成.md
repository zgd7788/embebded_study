# 阶段 4：LED1 闪烁裸机工程生成

日期：2026-11-04

## 生成内容

在 `project/stage_3/261102` 新增：

- `start/start.S`：关 IRQ/FIQ、设置栈顶、清 `.bss`，再调用 `main`；`main` 返回后停在死循环。
- `linker.ld`：将镜像链接到 `0xC0008000`，栈顶设为 `0xC1000000`，分离 RX 与 RW ELF 段。
- `main.c`：使能 A7 侧 GPIOZ AHB5 时钟，配置 PZ5 为低速推挽输出，然后周期调用 `HAL_GPIO_Toggle`。
- `Makefile`：使用 Cortex-A7 freestanding 参数构建 ELF、裸 BIN、反汇编和 map 文件。
- `README.md`：构建、U-Boot 加载约定和限制。

由于 `GPIOZ` 宏是 `volatile gpio_t`，将 GPIO API 的端口参数统一改为 `volatile gpio_t *`；另外 `gpio.c` 使用 `NULL`，补充 `<stddef.h>`。这些是严格目标编译中实际发现并解决的类型/头文件问题。

## 构建验证

在当前 Windows 工作区运行 `make clean all inspect` 成功，使用本机 `arm-none-eabi-gcc`。另以同一工具链对 `src/gpio.c` 与 `main.c` 运行 `-std=c11 -Wall -Wextra -Werror -fsyntax-only`，通过。

产物检查结果：ELF32 ARM、EABI5 soft-float，入口地址 `0xC0008000`；RX 段从 `0xC0008000` 开始；栈顶符号为 `0xC1000000`；`build/gpio_led.bin` 为 1492 字节。交叉构建和 ELF 检查不等于目标板运行验证。

## 运行前提和未验证项

此启动代码假设 U-Boot 已完成 DDR 初始化，且以 AArch32 特权上下文通过 `go 0xC0008000` 转入；没有建立异常向量、MMU、Cache 或定时器。不要从 Linux shell 跳入该裸机程序，因为 Linux 可能同时控制 GPIOZ。U-Boot 需要通过用户已有的 TFTP/SD 等传输方式把 BIN 放到 `0xC0008000`；TFTP 示例见工程 README。

当前主循环以 80,000,000 次 volatile 递减作为临时延时，频率取决于编译选项和 CPU 状态，只适合看 LED 是否翻转。下一步应在板上试跑；若不亮，先确认 PZ5/LED1 网络及有效极性、U-Boot 实际装载地址、GPIOZ 时钟和寄存器状态。尚未验证 PZ5 是否确为板上 LED1，也没有上板实测结果。

## 首次上板反馈（待诊断）

学习者报告通过 SecureCRT 串口在 U-Boot 执行 `loadb 0xc0008000`，随后发送文件，再执行 `go 0xc0008000`，开发板重启进入系统。还未提供发送文件名、loadb 显示的接收大小/完成状态、执行 `go` 前后的完整串口输出或复位耗时。已检查本地产物：`0xC0008000` 处为预期 ARM 启动指令，主循环预期不返回；不能据此证明板上收到的文件正确或已执行到 main。

排查顺序：确认 SecureCRT 使用 Kermit 与 `loadb` 协议匹配，发送 raw `build/gpio_led.bin` 而非 `.elf`，接收大小应为 1492 字节（`0x5D4`）；用 U-Boot `md.b 0xc0008000 0x10` 核对开头字节应为 `c0 00 0c f1 1c d0 9f e5 1c 00 9f e5 1c 10 9f e5`。这些是 ARM 指令在 little-endian BIN 中的实际字节顺序。之后记录 `go` 输出和从跳转到复位所经过的时间，以区分传输/镜像错误、MMIO 访问异常与看门狗超时。当前尚无复现日志，原因未定。

## 加载问题结论与板上验证

学习者确认首次误发的是 ELF 文件；改为发送 raw BIN 后，`go 0xc0008000` 可以运行并观察到 LED 现象。`loadb` 只负责协议传输并将文件字节写到给定 RAM 地址，`go` 直接跳到指定地址执行；该组合不会像 ELF loader 那样读取 ELF header、program header、按段复制到运行地址或设置 ELF entry。ELF 文件开头是 `0x7f 'E' 'L' 'F'`，所以从其首地址直接执行会把元数据当作指令，导致异常；BIN 去除了 ELF 元数据，文件偏移 0 对应链接地址 `0xC0008000` 的 `_start`。

本次板上现象确认 U-Boot 加载地址、启动代码和 PZ5 GPIO 闪烁路径基本可用。没有记录闪烁周期测量值；延时仍是粗略忙等，之后可通过定时器生成稳定节拍。
