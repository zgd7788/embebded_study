# 阶段4 I²C 状态快照与清标志

## 学习问题

学习者复盘 I2C_MasterReadByte，询问为什么向 ICR 写 STOPCF/NACKCF 清除标志后，再判断 status 中 NACKF 不会必然为 false。

## 对照当前代码

代码位置：project/stage_4/261122/drivers/mcu/src/i2c.c，第332行读取 ISR，第343行写 ICR 清标志，第345行判断局部变量 status。

```c
uint32_t status = I2Cx->ISR;
/* ... */
I2Cx->ICR = I2C_ICR_STOPCF_Msk | I2C_ICR_NACKCF_Msk;
if ((status & I2C_ISR_NACKF_Msk) != 0U)
```

赋值把 ISR 当时的数值复制到局部变量 status，status 不是寄存器别名，也不是指向寄存器的指针。ICR 对应位写1使硬件清除 ISR 中的 STOPF/NACKF，不会修改已保存的 status，因此仍能据清除前的快照判断本次事务收到过 NACK。

以只考虑这两个标志为例，读取时二者均为1，则 status 对应位为0x30；清除后 ISR 的两位变为0，status 的0x30仍保留，NACK判断为真。若改为清除后重新读取 I2Cx->ISR，在没有新事件的条件下就看不到刚才的NACK，丢失本次错误信息。

区分两处清除：START 前清除上次遗留标志，为本次访问准备；STOP 分支在已保存状态后清除本次完成/错误标志，再按快照返回。不是通过先清除后重新读硬件来判断旧事件。

## NACK 出现的场景

学习者继续询问什么情况下收到 NACK。说明每个地址或数据字节后的第9个时钟，由接收方决定应答：拉低 SDA 为 ACK，SDA 保持高为 NACK；可能是接收方不接受，也可能根本没有器件应答，NACK本身不能确定具体原因。

主机发送地址后，地址不匹配、器件未供电/仍在复位/未就绪，或连接、电平及时序异常使地址未被正确识别，都可能表现为没有 ACK。主机发送数据后，有些器件在忙或不接受该数据时会 NACK，具体由器件协议决定，不能一概认为访问任意无效寄存器必然 NACK。

结合当前 I2C_MasterReadByte：主机发送 0x95（0x4A 的读地址）后，从机若不应答会使 NACKF 置位，当前函数据此返回 -3。进入读数据阶段后，发送方是从机，接收方是主机；主机对末字节主动发送 NACK 表示结束接收，这是正常协议行为，不属于收到从机 NACK，不因此置当前主机的 NACKF。以正常读取 D9 对照地址阶段无人应答的流程说明区别。

## 继续复盘多字节接收循环

学习者表示继续学习。按昨晚约定先理解参考实现，本轮从 I2C_MasterRead 的接收循环讲解，不提前代写器件层或板级初始化。

结合已上板的 D9、00、AE 三字节说明：NBYTES=3 告诉硬件本次接收数量，received 从0开始记录软件已读取并存入数组的数量；每次 RXNE 表示 RXDR 有一个未读取字节，读 RXDR 后硬件清除对应接收就绪标志，软件递增 received。RXDR 一次访问取一个字节，不会因 length=3 而一次读出三个。示例依次写 data[0]=D9、data[1]=00、data[2]=AE，received 分别为1、2、3。

NBYTES 控制线上传输结束条件及末字节 NACK，received 用于软件缓冲区与数量核对。received 达到length后仍等STOP，且最后RXNE与STOP同时置位时先取RXDR再判STOP；只有无收到NACK、数量满足及检测到STOP才成功。后续再结合 main 复习MAP=0x81与器件地址自增，并逐步进入器件层封装。

## 主机读完后的主动 NACK

学习者追问“读字节的时候，主机不发送NACK嘛”。明确回复会发送：在当前 AUTOEND=1、RELOAD=0 的读取配置中，硬件依据 NBYTES 对前面的字节发送 ACK，对最后一个字节发送 NACK 并产生 STOP。单字节读取时，这一个字节就是末字节；三字节读取时 ACK、ACK、NACK。

再次限定当前主机模式中 NACKF 的含义为收到对方的 NACK，例如从机未确认主机发送的读地址；它不因主机主动发送正常结束读取的 NACK 而置位。因此“已发送末字节 NACK”和“未收到从机 NACK、返回成功”可以同时成立，软件无需在读取每个字节后另写 NACK 位。本轮只讲解与记录，无代码修改或新增测试，理解反馈仍待后续。

## 数据字节 AE 的含义

学习者询问“从机发送AE是什么意思”。澄清前例中的 AE 是省略0x前缀的十六进制数据0xAE，来自已验证的CS42L51寄存器0x03；它的8个数据位是10101110。连续读取0x01～0x03时，芯片依次发送D9、00、AE，主机存入接收数组。ACK/NACK是每个8位数据之后第9个时钟的应答，不是AE的数值含义。主机在收到最后一个数据字节AE后发送NACK，随后STOP；若寄存器值不同，线上数据随之不同，末字节结束规则不变。本轮仅解释，无代码或测试变化，不据此标记独立理解。

## 硬件判断末字节的依据

学习者继续问硬件如何知道哪个数据是最后一个。对应当前I2C_MasterRead配置，length通过移位写入CR2.NBYTES，提前告诉硬件本段接收字节数。例程传length=3，在RELOAD=0、AUTOEND=1时，硬件内部跟踪字节传输数量，对前两字节ACK，对第三字节NACK并STOP；不按0xAE这一数据内容判断结束。received是软件已从RXDR取出并存入数组的数量，不是控制硬件末字节应答的变量。只描述内部计数机制，不声称CR2.NBYTES可读字段会逐字节变化。此轮仅讲解，无新增源码或测试证据。

## MAP设置与功能寄存器读写的区别

学习者能复述验证函数先单读参考、发0x81、读三字节并打印的顺序，但不清楚具体向芯片哪个寄存器写/从哪里读。进一步解释CS42L51按事务内字节位置解码：写地址0x94后的第一个数据字节为MAP，后续才是待写入所选寄存器的数据。仅发MAP=0x81就STOP只更新内部访问指针和INCR，没有功能寄存器数据写入，也不需要先发送另一个MAP寄存器地址。

与先前[0x94][MAP=0x0C][数据FF]对照：后者的FF写入0x0C，前者[0x94][MAP=0x81]没有第三个待写数据字节。下一笔读事务使用芯片保存的指针，依次输出0x01、0x02、0x03的D9/00/AE；I2C_MasterRead无需再次带寄存器地址。接收数组随后用于输出和逐项比较参考值。将这个区别补充到手册索引的2.2节，依据为此前核对的图24/25及MAP说明。本轮只解释和维护记录，无驱动代码、构建或测试变化，理解反馈待后续。
